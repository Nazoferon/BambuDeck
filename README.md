# Проєкт: BambuDeck — локальний менеджер принтерів Bambu Lab (A-серія)

## 0. Роль і формат роботи
Ти досвідчений Python-розробник, що допомагає зробити кросплатформний застосунок
для локального керування 3D-принтерами Bambu Lab. Працюємо поетапно:
спочатку ядро + консольні тести, потім UI. Не переходь до наступного етапу,
поки поточний не підтверджено мною. Перед кодом коротко опиши план, після коду —
як це запустити й перевірити. Якщо щось у протоколі невідоме або суперечливе —
скажи прямо, не вигадуй; познач як [ПЕРЕВІРИТИ] і запропонуй спосіб перевірки
на реальному принтері.

## 1. Мета
Застосунок (спочатку ПК, потім Android), який замінює Bambu Handy для принтерів
у LAN mode (Orca Slicer не працює з хмарою Bambu). Підтримка кількох принтерів.
Ключові фічі: статус, температури, камера (слайдшоу), світло,
швидкість/вентилятори, керування друком і скасування окремих об'єктів під час друку
з візуалізацією силуету.

## 2. Середовище
- Принтер зараз: Bambu Lab A1 mini (0.4 сопло); у майбутньому A1 (більший стіл).
  Прошивка остання, LAN mode + Developer mode увімкнені.
- Принтери мають статичні IP з роутера, працюють у тій самій мережі, що й застосунок.
- Мова: Python 3.11+. UI: Flet. Цільові платформи: Windows/Linux (розробка), Android (APK).
- Залежності мінімальні й чисто-Python (для Android): `paho-mqtt`, стандартні
  `ssl`/`socket`/`asyncio`/`json`/`zipfile`/`ftplib`. Заборонено (без обговорення):
  OpenCV, numpy, Pillow як обов'язкові залежності (якщо Pillow потрібен для силуету —
  запропонуй альтернативу або обґрунтуй).
- Код: типізація (type hints), dataclasses/pydantic-подібні моделі, логування через
  `logging`, коментарі та докстрінги англійською, спілкування зі мною українською.

## 3. Архітектура (два шари, жорстке розділення)
```
bambudeck/
  core/                    # без жодних імпортів UI
    config.py              # профілі принтерів, збереження/завантаження
    models.py              # PrinterProfile, PrinterState, PrintJob, PlateObject...
    mqtt_client.py         # з'єднання, reconnect, парсинг report
    commands.py            # побудова JSON-команд (чисті функції, легко тестувати)
    camera.py              # клієнт порту 6000 (A1/P1), генератор кадрів
    ftp_client.py          # FTPS (порт 990, implicit TLS) для завантаження 3mf
    threemf.py             # парсинг 3mf: об'єкти, bbox, превʼю
    printer.py             # PrinterClient — фасад: стан + методи керування
    manager.py             # PrinterManager — колекція PrinterClient
  cli/                     # консольний тестовий інтерфейс (етап 1)
  ui/                      # Flet (етап 2+)
  tests/                   # pytest; юніт-тести без принтера + інтеграційні з прапорцем
```
Принципи: UI не знає про MQTT/сокети. Ядро спілкується з UI через
колбеки/події (`on_state_update`, `on_connection_change`) або asyncio-черги.
Кожен принтер — незалежний екземпляр; падіння одного не впливає на інші.

## 4. Профіль принтера
Поля: `id` (uuid), `name`, `ip`, `serial` (**обов'язково**, потрібен для MQTT-топіків),
`access_code`, `enabled`, `model` (необов'язкова довільна назва; відомі A1MINI/A1
додають специфічну схему столу й ліміти). Валідація: IP-адреса, access code
рівно 8 символів, serial не порожній. Самої назви недостатньо для LAN-з'єднання:
потрібні IP, SN і access code; незнана модель не блокує базове підключення.
Зараз профілі зберігаються у `printers.json` в корені проєкту. Код доступу
записується у відкритому тексті, як обрано для desktop-прототипу: захищай файл,
не надсилай його разом із логами та не додавай до публічного репозиторію.
Для Android перед релізом потрібно перейти на захищене сховище платформи.
Ніколи не логувати access code. Кілька принтерів можна додавати, редагувати й
видаляти без перезапуску.

## 5. Підключення
- **MQTT**: TLS, порт 8883, логін `bblp`, пароль = access code, сертифікат
  самопідписаний (вимкнути перевірку або pin; задокументувати).
  Топіки: `device/{serial}/report` (підписка), `device/{serial}/request` (команди).
  Тримати keepalive, автоперепідключення з експоненційною затримкою (1→2→5→10→30 с).
- Після підключення одразу `pushall`; далі повторювати періодично (~раз на 30–60 с),
  бо принтер частіше шле лише змінені поля. Стан = накопичений merge дельт, а не
  заміна всього об'єкта.
- **online/offline** визначається за свіжістю повідомлень: немає звітів >15 с →
  offline (і спроба reconnect). Не покладатися на ping.
- Принтер має ліміт одночасних MQTT-клієнтів: обробляти відмову підключення
  без падіння, показувати зрозумілу помилку («можливо, забагато клієнтів»).
- Унікальний `client_id` (щоб не вигнати Orca/Studio).
- Помилки автентифікації (невірний код) відрізняти від мережевих.

## 6. Стан принтера (мінімум полів)
`gcode_state` (IDLE/PREPARE/RUNNING/PAUSE/FINISH/FAILED), `mc_percent`,
`layer_num`/`total_layer_num`, `mc_remaining_time`, `subtask_name`/`gcode_file`,
`nozzle_temper`/`nozzle_target_temper`, `bed_temper`/`bed_target_temper`,
`spd_lvl`, `cooling_fan_speed`, `big_fan1/2_speed`, `lights_report`, `wifi_signal`,
`hms` (помилки/попередження), `print_error`, список пропущених об'єктів (`s_obj`)
[ПЕРЕВІРИТИ назви полів на реальному дампі].
Обовʼязково: режим `--dump` у CLI, що зберігає сирі JSON-звіти у файл —
на них будуємо парсер і тести.
Поле, якого немає у звіті, — `None`, не падати.

## 7. Керування (команди)
Усі команди будуються в `commands.py` як чисті функції → юніт-тести без принтера.
`sequence_id` унікальний для кожної команди.
- **Світло**: `ledctrl` [ПЕРЕВІРИТИ led_node для A1 mini — chamber_light чи work_light].
- **Температури**: `M104 S<t>` (сопло), `M140 S<t>` (стіл) через `gcode_line`.
  Ліміти за моделлю (A1 mini: сопло ≤300, стіл ≤80 [ПЕРЕВІРИТИ]). Валідація
  на рівні ядра, не лише в UI. **Заборонено під час друку/паузи** (state RUNNING/PAUSE/PREPARE).
  Кнопка «вимкнути нагрів» (S0).
- **Вентилятори**: `M106 P<n> S<0-255>`; UI показує 0–100%. Лише для підтверджених
  номерів вентиляторів моделі [ПЕРЕВІРИТИ P1/P2/P3].
- **Швидкість друку**: 4 профілі (silent/standard/sport/ludicrous) через команду
  `print_speed`; зворотне значення з `spd_lvl`. Доступно лише під час друку.
- **Ручний рух осей, homing (`HOME`) і park не підтримуються та не входять у
  скоуп проєкту**: ці дії не є практичними для цього сценарію керування через LAN.
- **Пауза / продовження / скасування друку**: дії доступні відповідно до стану;
  скасування має червону кнопку та окреме підтвердження, бо друк не можна поновити.
- Екструзія та операції завантаження філаменту — поза скоупом MVP.
- Усі команди повертають результат/помилку; жодних «тихих» провалів.
  Підтвердження ефекту — через наступний report (оптимістичний UI з відкатом).

## 8. Камера (A1/A1 mini)
- Протокол: TLS-сокет, порт 6000, пакет автентифікації 80 байт
  (константа, little-endian, логін `bblp` і access code, поля по 32 байти),
  далі потік: 16-байтний заголовок (розмір payload) + JPEG (SOI FFD8, EOI FFD9)
  [ПЕРЕВІРИТИ точний формат заголовка на прошивці].
- `camera.py` повертає async-генератор/колбек кадрів (bytes JPEG). Перевіряти
  валідність JPEG, відкидати битий кадр, не падати.
- Підключатися **лише коли відкрите вікно/CLI-режим камери**; відключатися при
  закритті. Одночасно лише один потік на принтер.
- Reconnect при обриві; таймаут, якщо кадрів немає >5–10 с.
- UI: показ як слайдшоу з оновленням `ft.Image` (мінімізувати мигання);
  індикатор «останній кадр N с тому». Кнопка «зберегти кадр».
- Опційно пізніше: запис таймлапсу з кадрів (збір у GIF/MP4 поза скоупом MVP).

## 9. Скасування об'єктів (ключова фіча)
Потік:
1. Дізнатися, який файл друкується (з `subtask_name`/`gcode_file`/URL у report).
2. Завантажити 3mf із принтера по FTPS (порт 990, implicit TLS, логін `bblp`,
   пароль = access code) у тимчасову теку; кешувати за назвою+розміром.
   Урахувати, що в LAN-режимі файл може бути в `/cache/` чи іншому шляху
   [ПЕРЕВІРИТИ].
3. Розпарсити 3mf (zip): `core/threemf.py` читає `Metadata/plate_N.json`
   (`bbox_objects`: id, name, bbox) і `Metadata/plate_N.gcode` (object label IDs,
   `M624` параметри, XY-точки та траєкторії екструзії перших п'яти шарів) окремо.
   Відповідність визначається геометричним
   зіставленням XY-точок із bbox; це висновок зі слайснутого G-code, а не гарантія
   протоколу `skip_objects`. Додатково: `Metadata/slice_info.config`,
   `Metadata/plate_N.png`. Визначити номер активної пластини.
4. Побудувати модель `PlateObject(id, name, bbox, polygon?)`.
5. UI: схема столу (розмір за моделлю) + доріжки екструзії перших п'яти шарів з G-code,
   підписані об'єктами; рамки показують їхній bbox. Можна вибрати шар або накласти
   попередні шари (увімкнено за замовчуванням, показується найвищий доступний шар);
   кожен об'єкт має власний колір, відтінки показують номер шару.
   Якщо в G-code немає траєкторій, відображається bbox. Label IDs зі звіту `s_obj` позначені сірим. Це список,
   повідомлений принтером, а не доказ того, що об'єкт фізично не надруковано.
   Клік по доступному силуету або прапорцю в рядку об'єкта перемикає його вибір;
   UI показує лічильник, назви вибраного та максимальну кількість об'єктів, яку
   можна вибрати. Кнопка пакетного пропуску відкриває одне підтвердження і
   надсилає всі вибрані G-code label IDs у `obj_list`. Не можна вибрати для
   відправлення всі об'єкти, що ще друкуються: щонайменше один має залишитися
   активним.
6. Після команди перевірити в наступних звітах, чи з'явився label у `s_obj`;
   окремо перевірити фізичний результат. Якщо принтер уже почав друкувати об'єкт,
   запит може бути запізнілим, навіть якщо label з'явився у звіті.
   `print.fun` bit 49 не є перевіреною ознакою підтримки skip і не використовується
   для блокування команди. Формат команди відповідає реалізаціям
   [Bambu Studio](https://github.com/bambulab/BambuStudio/blob/master/src/slic3r/GUI/DeviceManager.cpp)
   та [Home Assistant](https://github.com/greghesp/ha-bambulab/blob/main/custom_components/bambu_lab/pybambu/commands.py);
   спільнота описує ID як `identify_id` у
   [OpenBambuAPI](https://github.com/Doridian/OpenBambuAPI/blob/master/local-printer-api.md).
   У тесті на A1 mini (OTA `01.08.01.00`, MC `00.01.36.14`) Bambu Handy також
   показував Skip Object. 2026-10-23 LAN-команда для label `87` отримала ACK
   `success`, `s_obj` оновився до `[87]`, і користувач підтвердив, що куб було
   пропущено, а конус і текст продовжили друк. Це підтверджує роботу на цій
   конфігурації; інші моделі/версії прошивки та інші режими друку ще не перевірені.
   ACK або `s_obj` слід і надалі оцінювати разом із фізичним результатом.
Наступне покращення візуалізації: зіставлення траєкторій з превʼю `plate_N.png`
і вибір активної пластини в багатопластинних завданнях.
Винятки та крайні випадки:
- У G-code немає міток об'єктів («Label objects» вимкнено) → показати чітке
  пояснення, кнопки скасування неактивні.
- Файл не вдалося завантажити/розпарсити → деградація: показати список id без силуету.
- Один об'єкт на столі → попередити, що скасування = фактично зупинка.
- Не дозволяти скасувати вже пропущені; не дозволяти скасувати всі без явного
  підтвердження (запропонувати «Стоп»).
- Імена об'єктів можуть бути порожні/дублюватись → fallback «Об'єкт #id».
- Друк запущено з SD/хмари/іншого клієнта — файл може бути недоступний.
- Нова задача → скинути кеш об'єктів.

Перевірка команди на реальному принтері: запустити тестовий друк із кількома
об'єктами, переконатися, що друкується потрібна задача, і виконати
`python -m cli skip-object <G-code-label-id>`. CLI показує ID, вимагає окремого
підтвердження та перевіряє звіт `s_obj`, який сам по собі не підтверджує фізичний
пропуск. На A1 mini з OTA `01.08.01.00` та MC `00.01.36.14` контрольний
багатодетальний тест підтвердив фізичний пропуск label `87`. Для наступних тестів
використовувати багатошаровий друк, щоб уникнути запізнілої команди; тестувати лише
на завданні, яке можна перервати. Значення для команди — G-code label ID
(`unique label id` / `identify_id`), не `bbox_objects.id`.

## 10. UI (Flet; етап 3+)
**Головний екран**: окремі картки принтерів із назвою, моделлю, IP, станом і
прогресом активного завдання; під час друку показуються відсоток, залишок і
приблизний локальний час завершення. Натискання на картку відкриває детальне
керування вибраним принтером, не відключаючи інші. Усі увімкнені профілі
підключаються незалежно; помилка одного не зупиняє решту. Форма додавання/
редагування перевіряє поля та нагадує закріпити IP за принтером через DHCP
reservation у роутері. Код доступу зберігається у відкритому локальному JSON.
**Панель принтера** можна згорнути кнопкою або повторним натисканням картки;
схема столу не відображається без активного завдання з розібраними об'єктами.
Для моделі без відомої геометрії стола схема приховується, базове керування лишається.
**Панель принтера**:
1. Статус + температури (поточна/ціль).
2. Керування температурою (заблоковано під час друку, з поясненням чому).
3. Камера.
4. Світло (перемикач), вентилятори (слайдери), швидкість (4 сегменти).
5. Друк: повний статус, пауза/продовження/скасування, пропуск об'єктів зі схемою столу.
   Схема показує bbox та ID об'єктів, а також траєкторії перших п'яти шарів;
   вибір шару та накладання шарів допомагають розрізняти форму деталей.
   Скасування доступне під час RUNNING для багатодетального завдання після
   явного підтвердження; LAN-команду перевірено на A1 mini з конкретною версією
   прошивки, поведінка інших конфігурацій потребує перевірки.
Загальне: недоступні дії — disabled з підказкою, а не прихованi; індикатор
стану зʼєднання; помилки HMS людською мовою (мапа кодів — опційно пізніше).
UI має системну, світлу та темну теми, адаптивний розмір схеми столу й
компонування для вузьких екранів; ці поверхні ще потребують перевірки на телефоні.
UI-потік не блокується мережею (усе I/O асинхронне/в потоках).
Поточний desktop-прототип запускається з кореня проєкту командами
`pip install -r requirements.txt` і `python -m ui`. Він показує стан принтера,
завантажує 3MF активного друку через FTPS, малює силует перших шарів і дозволяє
вибрати один або кілька об'єктів для пропуску з підтвердженням. Підтримка
кількох пластин та перевірка адаптивного UI на Android лишаються наступними кроками.

## 11. Нефункціональні вимоги й винятки
- Помилки мережі не валять застосунок; усі виняткові ситуації логуються.
- Конфіг пошкоджений/відсутній → створити заново з резервною копією.
- Невірний access code / чужий serial → зрозуміле повідомлення.
- Принтер вимкнули посеред сесії → offline, команди відхиляються, не «висять».
- Ліміт частоти команд (rate limit), щоб не завалити принтер (особливо для
  регуляторів: відправляти після відпускання або з debounce).
- Android: фон/сон — зʼєднання можуть рватись; при поверненні в застосунок
  перепідключатися й робити `pushall`. Сповіщення в фоні — окремий етап, поза MVP.
- Безпека: код доступу не в логах, не в скріншотах, не в git. `.gitignore` для конфігу.
- Сумісність: A1 mini/A1 — повна; розширюваність на P1/X1 через `model` у профілі
  (різниця камери: P1 — порт 6000, X1 — RTSPS 322), але в MVP не реалізуємо.
